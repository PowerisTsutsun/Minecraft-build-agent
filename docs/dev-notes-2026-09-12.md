# Dev notes, 2026-09-12 — the bot is a blueprint bot

The natural-language planner and the mineflayer bot it ran on are gone. What is
left is the thing that was actually being used: drop a file into `schematics/`,
type `!build <name>`, get the build.

This supersedes the "Minecraft 26.1 sandbox (mineflayer bot, port 25566)"
section of `dev-notes-2026-09-06.md` and open issues 1 and 6 there, which were
about the plan format. Everything else in that file still holds — it is all
RCON-path.

## Why

The planner was the interesting half and the wrong product. It cost an API key
to run, it could seal its own door, and a model cannot be told "make an iron
farm that actually makes iron" — the thing that works is a capture of one that
did. Every build anyone reached for was already a file on disk. So the bot is
now the file half, finished, instead of two halves neither of which was done.

~6,000 lines of source, 12 test files, 2 MB of plan artifacts. The RCON path
lost nothing: it never imported any of it. That was checked by walking the
require graph from both entry points before anything was deleted, not by
grepping for imports.

**One function survived the cut.** `outsideIn` (sort a layer perimeter-first)
lived in `primitives.js` and is used by `schematic.js`. It existed because the
walking bot had to stand somewhere; the bot is gone, but `toBoxes` in
`commander.js` was tuned against that ordering and emits fewer `/fill`s with it,
so it moved into `schematic.js` with a comment saying so. Deleting it would have
changed build output, which a cleanup has no business doing.

## What arrived

`src/building/blueprints.js` — one place that turns a name someone typed into
something loadable:

1. `aliases.json` (hand-written nice names, and the only way to reach a
   `template:`), then
2. any blueprint file in `schematics/`, by its own lowercased basename.

An alias wins a clash, so renaming a file cannot silently change what an
existing name builds. The leading `/` is optional now — `/house1` is how the
list prints them, `house1` is what someone types after dropping `house1.schem`
in. `tools/rcon-build.js` resolves through the same module, so the console path
and the chat path cannot drift.

**The name off chat is only ever a key in a map.** It is never joined onto a
path. `!build ../../etc/passwd` resolves to null rather than reaching outside
`schematics/`, and `!build constructor` resolves to null rather than returning
an inherited member and dying later on `target.startsWith is not a function`.
`schematic.js` validates again at load; two checks, because this is the only one
that sees the raw chat string. `test/blueprints.test.js` covers both, plus
`__proto__`, the empty name, and a half-written `aliases.json` (which must
throw, not quietly report an empty catalogue — a bot that forgets every name
looks like the blueprints themselves vanished).

## Known gap

A dropped-in file builds by its filename but does **not** appear in
`!build list`, which is still built from `aliases.json`. `npm run catalog` names
anything new and closes the gap. `blueprints.names()` already returns the
un-aliased extras separately if the list should show them — that is a few lines
in `doBuild`, deliberately not taken yet.

## Suite

`npm test` — 5 files, 100 checks, no server needed:
`schematic-v3`, `boxes`, `blueprints`, `templates`, `rcon-build`.

`boxes.test.js` used the plan primitives to generate its fixtures. The merger
under test never cared where a block list came from, only what shape it is, so
the four generators it needed (floor, box, sphere, and a three-material
composite) are now local to the test file. `templates.test.js` lost its
classifier assertions with `src/pipeline/`.
